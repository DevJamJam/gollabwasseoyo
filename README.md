# 골라봤어요

원두를 살 때마다 세 개를 비교한다. 가격 보고, 용량 보고, 리뷰 뒤지고, 하나 고른다.

그런데 3개월 뒤에 다시 살 때가 되면 뭘 비교했는지도 왜 그걸 골랐는지도 기억이 안 난다. 사지 않은 후보 둘은 흔적도 없다. 그래서 매번 처음부터 다시 한다.

그 기록을 남기려고 만들었다. 구매 전에 고민한 후보, 실제로 산 것과 그 이유, 써보고 나서의 평가를 한 줄로 잇는다.

- 배포 — https://gollabwasseoyo.vercel.app
- Next.js 16 (App Router) · TypeScript · Tailwind v4 · Vitest · localStorage

첫날에 화면을 하나도 만들지 않았다. 이 앱의 핵심은 *"구매 기록이 없으면 고민 중, 있는데 평가가 덜 됐으면 구매 완료, 다 됐으면 평가 완료"* 같은 규칙인데, 이걸 홈 배지·상세 배지·필터 개수·진행률 바가 전부 같이 쓴다. 규칙이 틀리면 네 곳이 한꺼번에 틀린다. 그래서 규칙부터 순수 함수로 만들고 테스트로 묶어뒀다.

지금 저장소를 클론해서 열면 `Hello world!`만 나온다. 그게 정상이다.

## 뭘 하는 앱인가

아래는 아직 대부분 구현 전이다. 무엇을 만들 것인지의 목록이다.

- 후보를 최대 4개까지 나란히 비교한다. 1kg짜리와 500g짜리를 놓고 고민할 때 **100g당 가격으로 환산**해서 보여준다.
- 산 다음에는 실제 결제금액과 **왜 그걸 골랐는지**를 남긴다.
- 써보고 나서 별점·재구매 의사·한 줄 후기를 쓴다. 주문 단위가 아니라 **상품 하나하나에** 쓴다.
- 사지 않은 후보도 지워지지 않는다. 다음에 비슷한 걸 살 때 **그 후보를 그대로 불러온다.**
- 카테고리 7개 + 자유 태그로 찾는다.

자동으로 점수를 매겨 승자를 정하지는 않는다. 판단은 사람이 하고, 앱은 판단 재료를 정리해서 보여주고 결과를 잊지 않게 하는 데까지만 한다.

**안 만드는 것** — 로그인, 서버, DB, 상품 이미지, 쇼핑몰 정보 자동 수집, AI 추천, 가격 변동 추적, 배송비 자동 계산, 한 고민에 여러 주문, 휴지통.

## 데이터 구조

```
Decision (고민)
├─ 기본정보  제목 / 카테고리 / 태그[1~3] / 목적 / 예산?
├─ Candidate[1~4] (후보)
│    상품명 · 비교가격 · 브랜드 · 옵션 · 사용경험 · 구성량+단위
│    구매처 · 링크 · 배송메모 · 기대[0~3] · 걱정[0~3] · 메모
└─ Order | null (주문 0~1건)
     ├─ 구매일 · 최종 결제금액 · 구매처 · 이유
     └─ PurchasedItem[1~N]   ← candidateId로 후보를 가리킨다
          ├─ 실제 단가 · 구매 개수 · 실제 구성량
          └─ Review | null   ← 평가는 여기 안에
```

평가를 구매 상품 안에 넣은 게 이 구조의 핵심이다. "구매를 취소하면 평가도 사라진다"는 규칙이 있는데, 평가를 별도 목록으로 뒀다면 취소할 때마다 손으로 챙겨야 하고 한 번만 빠뜨려도 주인 없는 평가가 남는다. 안에 넣으면 `order = null` 한 줄로 끝난다.

`PurchasedItem`에는 따로 `id`를 두지 않았다. 한 주문에 같은 후보가 두 번 들어올 수 없으니 `candidateId`가 이미 유일하다. 안 쓰는 식별자를 만들 이유가 없어서, 평가 액션 시그니처도 `setReview(decisionId, candidateId, review)`가 됐다.

## 설계에서 신경 쓴 것

### 상태를 저장하지 않고 계산한다

`Decision`에 `status` 필드가 없다.

```ts
export function getStatus(d: Decision): DecisionStatus {
  if (!d.order) return 'considering';
  const allReviewed = d.order.items.every((it) => it.review !== null);
  return allReviewed ? 'reviewed' : 'purchased';
}
```

상태를 바꾸는 경로가 다섯 개다. 구매 등록, 구매 취소, 평가 작성, 평가 삭제, 고민 수정. 필드로 저장하면 이 다섯 곳 전부에서 같이 갱신해야 하고 하나만 빠뜨리면 화면이 거짓말을 한다.

이 선택의 값어치는 평가 삭제를 붙일 때 드러났다. *평가 완료 → 구매 완료*는 되돌아가는 방향의 전환인데, `removeReview`가 한 일은 `review = null` 하나였고 위 함수는 한 글자도 안 고쳤다. `status`를 저장했다면 정방향 네 개에 더해 역방향까지 구현해야 했을 거고, 역방향을 빠뜨리는 게 제일 흔한 버그다.

목록을 필터링할 때마다 다시 계산하는 비용은 있다. 기록 수백 건에서는 의미 없는 수준이고, 커지면 `useMemo`로 막으면 된다.

### 저장에 성공한 뒤에만 화면을 바꾼다

localStorage 저장은 실패할 수 있다. 용량이 찼거나, 시크릿 모드거나, 저장소가 차단됐거나.

```
흔히 쓰는 순서             이 프로젝트
setDecisions(next)         const r = save(next)
save(next)                 if (!r.ok) 안내만 하고 종료
                           setDecisions(next)
```

왼쪽 순서면 저장이 실패해도 화면은 성공한 것처럼 넘어가고, 새로고침하는 순간 데이터가 사라진다. 사용자는 뭘 잃었는지도 모른다.

낙관적 업데이트는 실패를 되돌릴 수 있을 때만 정당한데, 이 앱은 실패한 시점에 되돌릴 원본이 이미 없다. 그래서 모든 쓰기가 `commit()` 하나를 지나가고, 액션은 성공/실패를 담은 `ActionResult`를 돌려주고, 호출한 쪽은 성공일 때만 화면을 옮긴다.

### 폼이 들고 있는 값과 저장되는 값을 분리했다

`<input>`에서 나오는 값은 언제나 문자열이고, 라디오는 아무것도 안 고른 상태가 있다. 저장되는 데이터에는 그런 상태가 없어야 한다. 하나의 타입으로 둘 다 표현하려고 하면 반드시 어딘가 어긋난다.

```
FormValues   category: CategoryId | ''    budget: string     화면
    ↓ 검증 → 파싱
Input        category: CategoryId         budget?: number    액션 경계
    ↓ 저장
Decision     + id, createdAt, order                          저장
```

처음엔 폼 상태도 도메인 타입으로 표현했었다. 그랬더니 검증 함수의 `if (!v.category)`가 타입상 절대 참이 될 수 없는 **죽은 코드**가 됐다. 검증이 형식만 남아 있던 셈이다.

중간의 입력 타입에는 `order`가 아예 없다. 수정 액션을 `Partial<Decision>`으로 열어두면 폼 하나가 구매 기록과 평가까지 덮어쓸 수 있는데, 그 실수를 컴파일러가 잡아주지 못한다. 권한을 문서가 아니라 타입으로 적어둔 것이다.

### 자동 검색을 세 번 고치다가 결국 없앴다

제일 할 말이 많은 항목이다.

```
1차   useEffect([queryText, filters.q])
      타이머가 예약될 때의 filters를 붙잡고 있어서, 그새 바꾼 카테고리를 되돌려버림

2차   useCallback(..., [filters, router])
      필터가 바뀌면 타이머를 다시 예약. 그래도 router.replace()와
      새 props가 도착하는 사이의 틈은 남음

3차   ref 세 개로 방어 (타이머·최신 필터·포커스)
      응답 오기 전 의도를 ref에 보관. 그런데 뒤로가기와 입력창 포커스가
      겹치면 입력 문자열과 URL의 q가 여전히 어긋남

4차   자동 검색 제거. <form> submit 하나로 확정
      경쟁 상태가 생길 구조 자체가 사라짐
```

세 번 다 "타이머가 어느 시점의 상태를 보고 있느냐"는 같은 문제를 다르게 막은 거였다. 네 번째에 와서야 그 질문을 없앨 수 있다는 걸 인정했다.

잃은 건 타이핑에 결과가 따라오는 즉시성이고, 얻은 건 ref 세 개와 effect 두 개가 사라진 것, 홈 화면 상태가 입력 문자열 하나로 줄어든 것, 뒤로가기 동기화에 조건이 없어진 것이다. 수동 검증 항목도 "타이머 경쟁 상태 재현"에서 "Enter 눌러보기"로 바뀌었다. 사람이 손으로 확인할 수 있는 종류가 됐다.

정교하게 방어하는 것보다 방어할 필요가 없게 만드는 게 나을 때가 있다. 다만 이건 "자동 검색은 나쁘다"는 얘기가 아니다. 목록이 수천 건이거나 검색이 앱의 주 진입점이었다면 반대로 판단했을 거다. 7일이라는 예산과 이 기능의 중요도가 근거였다.

### 그 밖에

- **Server Component를 얇게 유지했다.** 데이터가 브라우저에만 있으니 서버는 URL 해석만 한다. 억지로 늘리면 존재하지 않는 데이터를 읽는 코드를 쓰게 된다.
- **필터는 URL이 유일한 기준이다.** `useSearchParams()`를 쓰지 않고 서버에서 한 번만 해석해 내려준다. 같은 정보를 두 경로로 읽으면 어느 쪽이 진짜인지 흐려진다.
- **후보 복사는 필드를 하나씩 나열했다.** `{ ...source }`로 쓰면 나중에 필드가 늘어날 때 복사하면 안 되는 것까지 딸려온다.
- **평가가 있어도 잠그는 범위는 최소로 뒀다.** 잠기는 건 어떤 후보를 샀는가뿐이다. 금액 오타 고치려고 평가를 지우게 만들 이유가 없다.
- **폼 라이브러리도 스키마 검증 라이브러리도 안 썼다.** 폼 상태 관리를 직접 해보는 게 이 프로젝트의 목적 중 하나다.

## 접근성

화면 작업과 함께 채워간다. 기준선은 이렇다.

모든 input에 `<label htmlFor>`, 에러는 `aria-invalid` + `aria-describedby`로 전달하고 제출 실패 시 첫 오류 필드로 포커스. 라디오 그룹은 `<fieldset><legend>`로 묶고 별점을 `<div onClick>`으로 만들지 않는다. 필터 칩은 `<button aria-pressed>`, 검색은 `<form role="search">`. 상태는 색만으로 구분하지 않고 텍스트를 항상 같이 쓴다. 모달은 `role="dialog"` `aria-modal`에 Esc 닫기, 열릴 때 첫 입력으로 포커스, 닫을 때 트리거로 복귀. `:focus-visible` 아웃라인은 지우지 않는다.

모달의 완전한 Tab 순환 트랩은 **선택으로 남겼다.** Esc·진입 포커스·복귀 포커스·`aria-modal`까지 있으면 스크린리더와 키보드 사용자가 모달을 인지하고 조작하고 빠져나올 수 있다. Tab 트랩을 직접 구현하는 건 가치가 있지만 난도가 높고 버그가 잘 생겨서, 7일 안에서는 앞의 네 가지를 확실히 하는 쪽을 골랐다.

## 알려진 한계

버그가 아니라 범위를 그은 결과다.

데이터가 브라우저에만 있어서 **다른 브라우저나 기기에서 접속하면 빈 화면이다.** localStorage는 주소 단위로 격리된다. 그래서 기록이 0건일 때 샘플 데이터를 넣어볼 수 있게 해뒀다. 같은 이유로 기기 간 동기화도 없고, 탭을 두 개 열어놓고 각각 고치면 나중에 저장한 쪽이 이긴다.

등록하다가 새로고침하면 입력이 날아간다. `sessionStorage`에 초안을 저장하는 것 자체는 금방이지만 복원 안내·만료·탭 충돌까지 하면 범위가 커져서 이번엔 안 한다.

한 고민에 주문은 하나만 기록한다. 배송비·쿠폰·할인은 쪼개지 않고 최종 결제금액만 남긴다. 후보는 최대 4개다. 같은 상품을 여러 고민에서 불러오면 각각 독립 복사본이 되므로 "이 상품의 전체 구매 이력" 같은 화면은 만들 수 없다.

구매만 하고 평가를 안 쓴 후보는 **써봤는지 앱이 알 수 없다.** 원두를 샀지만 개봉하지 않았을 수도 있으니까. 그래서 추측하지 않고 원래 값을 그대로 둔다.

### 저장소 검증은 일부러 느슨하다

localStorage를 개발자 도구로 고쳐도 앱이 안 죽게 막긴 한다. 다만 목표는 **화면을 즉시 깨뜨리는 값을 걸러내는 것**이지 데이터가 정확하다고 보장하는 게 아니다.

`brand`에 객체가 들어 있거나, 문자열 배열에 숫자가 섞여 있거나, 존재하지 않는 후보를 가리키는 주문이 있으면 손상으로 판정하고 빈 상태에서 시작한다. 그리는 순간 터지는 값들이다.

반대로 기대되는 점이 규칙상 3개인데 4개 들어 있으면 **그냥 통과시킨다.** 여기서 손상 판정을 내리면 항목 하나가 많다는 이유로 사용자 기록 전체를 날려버리게 된다. 손실이 문제보다 크다. 이런 값은 폼 검증과 저장 직전 불변식이 잡는다.

### 서버로 옮긴다면

바꿀 곳은 `storage.ts`의 `load`와 `save` 두 함수뿐이다. 컴포넌트는 `localStorage`라는 단어를 모르고, 모든 변경이 `useDecisions()`가 내주는 액션을 통해서만 일어난다. 액션이 이미 `ActionResult`를 돌려주고 있어서 `Promise<ActionResult>`로 바꿔도 호출하는 쪽 코드는 그대로 쓸 수 있다.

## 만들면서 겪은 것

코드를 쓰기 전에 설계를 먼저 잡았는데, 그 과정에서 모순이 꽤 나왔다.

**구매를 사용 경험이랑 같은 걸로 봤던 것.** 과거 후보를 불러올 때 "샀으니까 써봤겠지" 하고 사용 경험을 자동으로 바꿔줬었다. 근데 원두를 사놓고 안 뜯었을 수도 있다. 확실한 근거는 구매가 아니라 **평가의 존재**다. 별점이랑 후기를 쓰려면 실제로 써봐야 하니까. 반대로 평가가 없다고 안 써본 건 아니라서, 그 경우엔 추측하지 않고 원래 값을 유지하기로 했다.

**문서가 코드보다 과하게 잠갔던 것.** 평가가 달린 뒤 구매 정보를 어디까지 고칠 수 있냐는 규칙인데, 코드는 "어떤 후보를 샀는가"만 잠그고 있었는데 문서는 "구매 정보 전체 수정 불가"처럼 써놨었다. 문서만 보고 구현했으면 입력칸을 전부 비활성으로 만들었을 거다. 문서가 코드보다 세게 잠그는 것도 버그다.

첫날 코드를 쓰면서 겪은 것도 몇 개 있다.

`0.3 * 3`이 `0.8999999999999999`다. 구성량에 소수를 허용하니 총 구매량 계산에서 바로 튀어나온다. 반올림을 여기저기 넣으면 어디서 값이 바뀌었는지 못 쫓아가니, 화면에 그리기 직전 한 곳에서만 처리하기로 했다. 계산 함수는 반올림하지 않는다는 것 자체를 테스트로 박아뒀다.

`2026-02-30`을 `new Date()`에 넣으면 에러 없이 3월 2일이 된다. 그래서 만든 다음에 연·월·일을 되물어서 확인한다.

`crypto.randomUUID()`는 HTTPS랑 localhost에만 있다. 나중에 실기기를 로컬 IP로 열어볼 때 없어서 저장이 터질 자리라, 폴백을 다섯 줄 넣어뒀다.

그리고 설계 문서에 컴파일 오류가 있다고 판단했는데 **아니었다.** TypeScript 4.4부터 조건식을 `const`에 담아두면 좁힘이 유지된다는 걸 몰랐다. `npx tsc --noEmit` 한 번이면 30초 만에 확인할 수 있는 걸 추측으로 말했다. 확인하고 말할 것.
